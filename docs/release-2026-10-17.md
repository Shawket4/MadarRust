# Release 2026-10-17: DB architecture Phases 2, 3 and 5

Plan of record: `DB_ARCHITECTURE_AUDIT_2026-10-16.md` (§8 Phases 2, 3, 5; §7 compat; §10 no data loss).
Branch: `feat/db-phase2-3-5` (contains main through v1.11.0: Phases 0, 1, 4, 6).

Hard rules that hold for everything below:
- No data loss. Nothing is dropped that holds data. Retired tables move to the `archive` schema; every data move is an
  idempotent backfill with a reconciliation that must match.
- Old tills keep their exact contracts. No minimum-version row is seeded, and nothing forces an update.
- Anything gated on time (30 days of zero usage, every device on a new build) is written but PARKED under
  `migrations/parked/`, with its condition in the file header. Nothing parked is applied by this release.

Also rerun the drift check on the new dump (§9.4): build `drift_prod` from the new dump's `--schema-only` and compare it
with `drift_fresh` (the CI `schema-drift` job). The expected drift is `deploy/schema/drift_expected.txt`: only the stray
`_sqlx_test` schema. Anything else means someone hand-applied something to prod since 2026-09-05. Stop and read it.

## 2. Verify each phase: one command each

```bash
scripts/db_verify_phase.sh 2 madar_fresh
scripts/db_verify_phase.sh 3 madar_fresh
scripts/db_verify_phase.sh 5 madar_fresh
```

Each command:
1. clones `madar_fresh` into `madar_fresh_verify_p<N>`;
2. migrates the clone to the state just before the phase;
3. captures the BEFORE state;
4. applies the phase and runs its backfills twice;
5. captures the AFTER state and checks every gate.

It exits 0 only when every gate passes, and writes its evidence to `db-verify-p<N>-<timestamp>/`. The phases build on
each other: the Phase 3 run applies Phase 2 first as part of "before Phase 3", and so on.

Gates, and what each means:

| Gate | Evidence file | Meaning |
|---|---|---|
| `OK reconcile` | `reconcile.diff` empty | `scripts/db_reconcile.sql` per org: counts and money/qty sums of every ledger table are byte-identical before and after. No row and no piastre moved. Phase 5 adds metrics on purpose; those are listed in `scripts/db_reconcile_expected_p5.txt`, and every other line must still match. |
| `OK visible rows per org` | `visible.diff` empty | `scripts/db_rls_visibility.sql`: for every org and every RLS table, the rows a tenant session (`madar_app`) sees (count + md5 of primary keys) are identical. The RLS policy changes cannot widen or narrow what any shop sees. |
| plan table, no `<-- slower` | `plans.txt` | `scripts/explain_hot_paths.sql`, as owner and as `madar_app`. A query flagged slower by > 25 % AND > 1 ms fails the gate. |
| `OK db_phase<N>_check` | `check.tsv` empty | The phase's structural checks (flat policies, NOT NULL, no INVALID index, no leftover global unique, legacy names are views, ...). |
| phase1 check | `phase1_check.tsv` empty | Phase 1's invariants still hold. |
| backfill idempotency (Phase 5) | `backfill_run2.tsv` | The second run of every backfill changes 0 rows. |

## 3. Deploy order

Deploys are push-to-main CI. Before the new container migrates, the deploy dumps prod to `/opt/madar-rust/db-backups`
(the last 10 are kept). Migrations run on boot. Ship one phase per release, in this order, and do the watch step before
the next:

1. **Phase 2.** Migrations `20261018*`.
   - Consumer impact: none required. The dashboard no longer calls the 15 retired write routes (they were already
     failing in prod). Regenerate the dashboard's orval client from `openapi.json` in the same release (lockstep). No
     POS change.
2. **Phase 3.** Migrations `20261019*`.
   - What changes: the server's own reads use the unified catalog tables, the old-shape routes read `compat.*`, and
     the `included_option_ids` allowlist moves to `menu_item_modifier_group_options` (dual-written by trigger).
   - Consumer impact: none. Every old response shape is unchanged and pinned by `tests/compat_contract_tests.rs`.
   - Parked, with their conditions in each file: dropping the public compat views (one release later), the array
     column (after a clean `db_phase3_check` on live prod), and the `legacy_*` columns.
3. **Phase 5.** Migrations `20261020*`.
   - Ledger FKs from org/branch now RESTRICT; `DELETE /tills/{id}` is a soft delete (same 204).
   - Unified `ref_counters`, dual-written and serialized on the old table's row lock, so a rolling deploy cannot mint
     a duplicate ref.
   - `loyalty_customers` is renamed `loyalty_memberships`, with an updatable compat view under the old name.
   - bigint `_wide` twins of the till and loyalty totals.
   - Relational dine-in lines (columns + add-on / optional child rows), dual-written by trigger from `line`.
   - Consumer impact: `OpenTicketItemView` gains `item_name` / `quantity` (additive), so regenerate the dashboard
     client. No POS change is required.
   - Parked, with their conditions: the ref-counter, money-width and ticket-line JSON contracts; the compat view drop;
     the kitchen generated columns; `client_key NOT NULL`.

## 4. What to watch after each deploy

All phases:
- Boot log: every migration line `Applied …` with its duration, then the server listening. A migration that waits on a
  lock gives up at its `lock_timeout` (15 s), the boot fails and the container restarts; the migration is idempotent and
  retries. Several restarts in a row means a long transaction is holding a lock: find it in `pg_stat_activity`.
- `migrate_guard` warnings (`dropping the INVALID index …`) mean a CONCURRENTLY build failed once and is being rebuilt.
  One is fine; one on every boot is not.
- Afterwards, run read-only on live prod: `psql "$PROD" -X -At -F $'\t' -f scripts/db_phase<N>_check.sql` must print
  nothing.

Phase 2 specifically:
- Errors `42501` / "row-level security" or `22P02` / "invalid input syntax for type uuid" in request logs mean a request
  reached a tenant table without an org stamped (a fail-closed bug, never a leak). Rare and specific: report the route.
- `410 SHIM_WRITE_REMOVED` hits, counted in `compat_usage` under kind `shim_write_gone`. Expected: zero (no client calls
  those routes).
- `23505` on `uq_orders_org_idem` / `uq_orders_org_order_ref` is the idempotent-replay path. The response is the
  existing order (200), not an error.
- Public pages (shop subdomain, QR table, online order, loyalty card, booking page, wallet pass refresh) now run under
  RLS through `PublicDb`. Check that one of each still loads.
- Reports from rollups: the worker logs `madar.rollups`; `MADAR_REPORTS_FROM_ROLLUPS=0` puts every report back on
  the live computation (rollback switch, no deploy needed).
- Order create (2.6b, 20261018310000): the rollup dirty-marks no longer run for a sale rung up now. Postgres time
  per order create should be at or below v1.10.0 (pgbench on the copy: 3.65 ms v1.10.0, 2.70 ms after; it was
  7.25 ms with the 2.6 triggers). `sales_daily_dirty` should hold only late replays / voids / refunds of old days,
  and empty out within one worker pass (5 min) or at the next till close of that branch.

Phase 3 specifically:
- The menu, the storefront menu and order pricing are read from the unified tables. Watch for 5xx on
  `/menu-items`, `/public/branches/{id}/menu` and order create. After the first orders, `scripts/db_phase3_check.sql`
  on live prod must print nothing.

Phase 5 specifically:
- A `23503` on deleting a branch or an org means a ledger now blocks a hard delete. That is intended: those are
  soft-deleted in the app.
- Ticket fires and delivery checkouts mint refs through `ref_counters`. A `23505` on `uq_open_tickets_org_ref` /
  `uq_delivery_orders_org_ref` would mean a counter collision: report it immediately.
- `scripts/db_phase5_check.sql` on live prod after the first tickets must print nothing.
